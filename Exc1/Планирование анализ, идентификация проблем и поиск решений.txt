Анализ проблем в текущей архитектуре
Исходя из описания системы и того, что сайт «Александрит» подключён к Яндекс Метрике, но начал работать через API для оформления заказов, можно выделить следующие проблемы:
	1.  Отсутствие полной картины метрик
			Яндекс Метрика фиксирует только действия пользователей на сайте, но не учитывает заказы, оформленные через API.
			Это приводит к тому, что аналитика и бизнес-метрики не отражают реальную ситуацию.
	2.  Потенциальные проблемы с нагрузкой на API
			Если заказов через API становится больше, может возникнуть вопрос масштабируемости.
			Отсутствие мониторинга API-метрик может привести к неожиданным сбоям.
			Неизвестно, какой максимальный уровень нагрузки может выдержать API.
			Нужны инструменты предсказания нагрузки, возможно, анализ с помощью Queuing Theory.
	3.  Отсутствие централизованного мониторинга
			Не ясно, как сейчас отслеживаются ошибки, задержки и проблемы производительности.
			Если сбои происходят на стороне API, могут быть сложности с их своевременным обнаружением.
			Важно добавить распределённые трассировки (например, OpenTelemetry) для лучшего анализа задержек.
	4.  Нет информации о поведении пользователей в API
			Кто чаще всего оформляет заказы через API?
			Какой процент заказов идёт через API, а какой остаётся на сайте?
			Как изменяется поведение клиентов при изменениях в API?
	5.  Риски потери заказов или ошибок в обработке
			Если API падает или работает нестабильно, могут быть заказы, которые теряются или обрабатываются некорректно.
			Нужно фиксировать ошибки, тайм-ауты, повторные попытки отправки данных.
			Возможно, требуется добавить идемпотентность для предотвращения дублирующих заказов.
	6.  Проблемы с контрактами API
			Насколько легко вносить изменения в API без нарушения обратной совместимости?
			Существуют ли версии API или приходится менять контракты без учёта старых интеграций?
			Клиенты API могут столкнуться с проблемами, если контракты меняются без предупреждения.
			Важно ввести версионирование API и строгие контракты (например, OpenAPI/Swagger).
	7.  Соблюдение микросервисных паттернов
			Используются ли транзакционные границы между CRM и MES?
			Как API обрабатывает отказоустойчивость, ретраи и дедупликацию запросов?
			Если какой-то из ключевых паттернов не соблюдается, это может привести к сбоям или потере данных.
			Возможно, стоит добавить Saga Pattern для управления распределёнными транзакциями.
	8.  Проблемы с интерфейсом
			Первая страница MES загружается долго, даже после введения фильтрации и пагинации.
			Операторам важно видеть последние заказы, но система не обеспечивает нужную скорость работы.
			Возможно, тормоза связаны с неоптимальными запросами к базе данных или отсутствием индексов.
			Важно провести профилирование SQL-запросов и проверить возможность кэширования данных.

Список инициатив для устранения проблем
	1.  Внедрение расширенного мониторинга API
			Фиксация успешных и неуспешных запросов к API.
			Логирование времени ответа и ошибок.
			Включение трассировки запросов через OpenTelemetry.
	2.  Настройка бизнес-метрик для заказов
			Ввод метрики: процент заказов через API vs. через сайт.
			Анализ поведения пользователей в API (количество клиентов, частота заказов и т.д.).
	3.  Сбор технических метрик API
			Ошибки HTTP (500, 400, 429 и т.д.).
			Время ответа на запросы.
			Количество запросов в секунду.
			Количество активных клиентов API.
	4.  Выбор и настройка системы мониторинга (Prometheus, Grafana, ELK и др.)
			Определение инфраструктуры для хранения и анализа логов.
			Визуализация данных через дашборды.
	5.  Настройка алертов на критические сбои API
			Если процент ошибок превышает порог – уведомление в Slack или другую систему.
			Если API медленно отвечает – оповещение DevOps/разработчиков.
	6.  Анализ нагрузки и масштабируемости API
			Можно ли выдерживать увеличение нагрузки без падений?
			Нужны ли горизонтальное масштабирование или кэширование?
			Проведение нагрузочного тестирования API.
			Возможно, использование Rate Limiting и Circuit Breaker.
	7.  Улучшение контрактов API
			Введение версионирования API.
			Описание контрактов с помощью OpenAPI.
			Введение backward-compatible изменений.
	8.  Оптимизация интерфейса MES
			Анализ скорости запросов на дашборде.
			Проверка индексов и оптимизация SQL-запросов.
			Кэширование результатов, если это возможно.
			Использование Materialized Views для ускорения сложных запросов.

Приоритизация инициатив (что делать в первую очередь)
Если есть возможность выполнить только три задачи в ближайшие полгода, выбрал бы:
	1.  Внедрение мониторинга API (технические метрики)
			Это позволит понять, насколько API стабилен, где основные проблемы.
			Фиксация ошибок, тайм-аутов, нагрузки.
			Добавление трассировки для поиска узких мест.

	2.  Настройка бизнес-метрик заказов через API
			Важно для понимания реального влияния API на бизнес.
			Процент заказов через API vs. сайт поможет в будущем принимать решения по развитию.

	3.  Оптимизация интерфейса MES
			Так как операторы зависят от скорости работы дашборда, его оптимизация критична для работы сотрудников.
			Возможно, потребуются SQL-индексы, кеширование или изменение архитектуры запросов.
			Анализ производительности и использование профилирования запросов.

Целевая архитектура через 6 месяцев
	• 	В системе настроен централизованный мониторинг API и заказов.
	• 	Есть визуальные дашборды, показывающие состояние API и бизнес-метрики.
	• 	Разработаны алерты, предупреждающие о сбоях.
	• 	Улучшена обработка заказов через API с учётом возможных отказов.
	• 	Оптимизирована работа интерфейса MES, устранены основные проблемы с тормозами.
	• 	Введено версионирование API, упрощена поддержка контрактов.
	• 	Проведено нагрузочное тестирование API, есть понимание его пределов и возможностей масштабирования.
	• 	Используются отказоустойчивые механизмы, такие как Saga Pattern и Circuit Breaker.
