Выбор и настройка мониторинга в системе
1. Мотивация
    Система «Александрит» изначально использовала Яндекс Метрику для мониторинга пользовательской активности. Однако с добавлением API для оформления заказов стало очевидно, что имеющиеся данные больше не дают полной картины происходящего в системе. Это приводит к следующим проблемам:
    •	Отсутствие видимости запросов, приходящих через API.
    •	Невозможность оперативного обнаружения проблем с доступностью сервисов.
    •	Сложность в анализе производительности и пропускной способности системы.
    •	Отсутствие информации о нагрузке на базу данных и другие критические компоненты.
    Введение мониторинга позволит:
    •	Выявлять узкие места в производительности API.
    •	Реагировать на сбои до того, как они затронут пользователей.
    •	Оптимизировать использование ресурсов и инфраструктуры.
    •	Улучшить пользовательский опыт благодаря оперативному обнаружению и устранению проблем.
2. Выбор подхода к мониторингу
    Для разных компонентов системы выбраны разные подходы:
    •	API-сервисы: используем подход RED (Requests, Errors, Duration), так как он позволяет мониторить количество запросов, ошибки и задержки в ответах.
    •	Инфраструктура (БД, серверы): используем USE (Utilization, Saturation, Errors), так как он ориентирован на загрузку ресурсов и помогает выявлять проблемы с их нехваткой.
    •	Общий мониторинг: применяем концепцию «Четырех золотых сигналов» (latency, traffic, errors, saturation) для комплексного контроля над работой системы.
3. Метрики и их назначение
    API-сервисы:
    •	Количество запросов (RPS) для интернет-магазина, CRM и MES API.
    		Зачем: Позволяет понимать нагрузку на систему.
    		Ярлыки: endpoint, user_id.
    •	Количество ошибок HTTP 500 для API.
    		Зачем: Помогает оперативно обнаруживать сбои.
    		Ярлыки: endpoint.
    •	Время ответа (latency) для API.
    		Зачем: Определение проблем с производительностью.
    		Ярлыки: endpoint.
Инфраструктура:
    •	CPU % и Memory Utilization для API и БД.
    		Зачем: Контроль потребления ресурсов.
    		Ярлыки: instance_id.
    •	Количество соединений с базами данных.
    		Зачем: Определение перегрузки базы.
    		Ярлыки: db_instance.
    •	Размер базы данных (shop, MES).
    		Зачем: Отслеживание роста данных.
    		Ярлыки: db_instance.
4. План действий
    1.	Развернуть Prometheus для сбора метрик и Grafana для визуализации.
    2.	Настроить экспорт метрик из API через Prometheus Exporter.
    3.	Подключить мониторинг баз данных (PostgreSQL, MySQL) через node_exporter.
    4.	Определить пороговые значения для метрик и настроить алерты.
    5.	Настроить дашборды для визуального контроля состояния системы.
    6.	Провести тестирование системы мониторинга, убедиться, что данные собираются корректно.
    5. Пороговые значения и реакции
Пороговые значения:
    •	CPU % > 85% в течение 5 минут → создается тикет DevOps.
    •	Ошибки HTTP 500 > 2% от общего количества запросов → оповещение команды разработки.
    •	Время ответа API > 1.5 сек в 95-м перцентиле → уведомление в корп. чат.
    •	Количество соединений с БД > 90% от максимума → анализ нагрузки, возможное масштабирование.
    •	Размер БД > 90% от доступного места → предупреждение DevOps о необходимости расширения.
Автоматизация реакции на события:
    •	оповещения для оперативного реагирования в корп. чат.
    •	Автоматическое масштабирование при росте нагрузки (если платформа поддерживает).
    •	Создание тикетов в менеджере задач при критических сбоях.
